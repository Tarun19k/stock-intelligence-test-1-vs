# Trimurti-Based UI/UX Operating Model

Source: `Knowledge Repository/AlphaVeda_idea` PDF, pages 1-8, 24-43. This file is the framework
overview; see `brahma-gates.md`, `vishnu-gates.md`, `shiva-gates.md` for the per-role review
scorecards, and `OFFSET_HARVEST_YIELD_FOUNDATION.md` for how this maps onto Offset/Harvest/Yield
specifically.

## The three roles

| Role | Product responsibility | Core question |
|---|---|---|
| Brahma — Understand and Create | Research people, behaviours, needs, risks, decision context | What should exist, for whom, and why? |
| Vishnu — Preserve and Operate | Design a stable, understandable, trustworthy user experience | How should the experience guide users without destabilising good behaviour? |
| Shiva — Review and Transform | Challenge assumptions, detect failure, remove weak patterns | What should be corrected, simplified, retired or rebuilt? |

**Not a one-shot pipeline.** The framework does not mean Brahma creates once, Vishnu maintains
forever, Shiva reviews only at the end. Every major feature — including Offset, Harvest, and
Yield — passes through all three roles, every time it changes.

```
Human psychology and behaviour research
          |
   BRAHMA -- Definition
          |
    Product planning
          |
   VISHNU -- UX Design
          |
 Prototype and implementation
          |
   SHIVA -- Review
          |
Evidence, learning, controlled change
          '---------> back to Brahma
```

## Combined alignment with Offset/Harvest/Yield (source pp.26-27)

Each trigger contains its own internal Trimurti cycle — no trigger is permanently owned by one
role:

| Portfolio mechanism | Primary Trimurti force | Supporting forces |
|---|---|---|
| Offset | Vishnu — preservation | Shiva removes excess; Brahma creates replacements |
| Harvest | Shiva — realisation and transformation | Vishnu prevents unnecessary harvesting; Brahma determines reuse |
| Yield | Brahma — new value creation | Vishnu preserves suitability; Shiva rejects weak yield sources |

## Why this matters for AlphaVeda specifically

This session's own recurring failure pattern — UI built ahead of real data (portfolio ledger),
declared "done" without a Shiva-class verification pass — is exactly the Brahma-without-Shiva gap
this framework exists to prevent. The sequencing gate adopted 2026-07-30 (no further OHY UI until
the ledger + reconciliation test exist) is a direct, if informally-arrived-at, application of this
framework's own discipline.
